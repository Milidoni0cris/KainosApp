Glosario técnico — qué es cada cosa

JavaScript — conceptos del lenguaje

Función flecha (=>)
Sintaxis corta para escribir funciones: (req, res) => { ... } es lo mismo que function(req, res) { ... }. Se usan todo el tiempo como funciones que se pasan de argumento a otra cosa (ver "callback").
Callback
Una función que se pasa como argumento a otra, para que esa otra la llame en el momento que corresponda — no corre donde se la escribe, sino después, cuando ocurre algo puntual. app.listen(PORT, () => {...}): esa función flecha es un callback que Node ejecuta una sola vez, apenas el servidor queda escuchando. Los handlers de ruta de Express también son callbacks: Express los llama cuando llega un pedido que matchea esa ruta.
Promise
Un objeto que representa un valor que todavía no está, pero va a estar (o va a fallar) en el futuro — típicamente el resultado de algo que tarda, como una consulta a una base o un pedido de red. pool.query(...) devuelve una promise, no el resultado directo.
async / await
Forma de trabajar con promises que se lee como código síncrono, de arriba a abajo, en vez de anidar callbacks. await algo() pausa esa función hasta que la promise se resuelve, y sigue con el valor real. Toda función que usa await adentro tiene que estar marcada async.
Desestructuración
Sacar valores de un objeto directo a variables, sin escribir objeto.campo cada vez. function crear({ categoria_id, nombre, tipo }) desestructura el objeto que llega como argumento — equivale a recibir datos y después hacer datos.categoria_id, etc., pero en una sola línea.
Operador || como valor de respaldo
process.env.PORT || 3000: si lo de la izquierda es "falsy" (undefined, null, 0, ''), usa lo de la derecha. Forma corta de decir "usá esto, y si no está, usá este otro valor".
Módulos (import / export)
Forma moderna de dividir código en archivos y compartir funciones entre ellos. export marca algo como disponible para otros archivos; import lo trae. Habilitado por "type": "module" en package.json — sin eso, Node esperaría la sintaxis vieja (require/module.exports, CommonJS).
Clases y herencia (class X extends Y)
AppError extends Error crea una clase que hereda todo el comportamiento de la clase nativa Error de JS (mensaje, pila de llamadas) y le suma algo propio (statusCode). super(message) en el constructor es obligatorio al extender una clase — le pasa ese valor al constructor de Error, que es quien lo guarda de verdad en .message.

Node.js — el entorno que ejecuta el código

process.env
Objeto global con las variables de entorno — valores definidos por fuera del código, en .env o por el sistema/hosting.
--watch
Bandera nativa de Node que reinicia el proceso al detectar un archivo modificado — usada en el script "dev", en vez del paquete nodemon.
--env-file=.env
Bandera nativa que carga las variables de un archivo .env dentro de process.env, sin necesitar el paquete dotenv.

Express — el framework del servidor

Middleware
Una función que se ejecuta en el medio del camino de un pedido HTTP, con la forma (req, res, next) (o (err, req, res, next) si es manejador de errores). Puede leer o modificar el pedido, responder directamente, o dejar pasar al siguiente middleware llamando a next(). express.json(), cualquier app.use(...), y hasta las funciones de ruta son, técnicamente, middlewares.
req (Request)
Objeto con todo lo que vino en el pedido: req.body (el JSON mandado, si lo hay), req.params (valores tomados de la URL, como el :id), req.query (parámetros después del ? en la URL — todavía no los usamos).
res (Response)
Objeto para construir la respuesta. res.json(objeto) la manda como JSON con el header correcto; res.send(texto) manda lo que sea y Express adivina el tipo; res.status(codigo) fija el código HTTP antes de mandar el cuerpo.
next()
Avanza al siguiente middleware en la fila. next(err) corta ese flujo normal y salta directo al manejador de errores (el middleware de 4 parámetros, registrado al final).
Router()
Una mini-app de Express para agrupar rutas relacionadas, que después se "monta" en la app principal bajo un prefijo con app.use('/prefijo', router).
Verbos HTTP y su significado
GET lee sin modificar nada; POST crea algo nuevo; PUT actualiza un recurso completo; DELETE sugiere "eliminar", aunque en Kainos nunca borra de verdad — ver el borrado lógico en la bitácora de SQL.

HTTP — códigos de estado que usamos

CódigoCuándo se usa
200 OKPedido exitoso, por defecto (GET, PUT)
201 CreatedSe creó un recurso nuevo (POST exitoso)
204 No ContentÉxito, pero no hay nada para devolver en el cuerpo (DELETE exitoso)

PostgreSQL + pg — acceso a datos desde Node

Pool
Mantiene varias conexiones abiertas a Postgres y las reparte entre pedidos concurrentes, en vez de una sola conexión que haría cola.
Consultas parametrizadas ($1, $2, ...)
Forma segura de meter valores externos en una consulta SQL — pg los trata siempre como datos, nunca como código, lo que evita la inyección SQL.
result.rows
Siempre un arreglo, sin importar cuántas filas devuelva la consulta (0, 1 o muchas) — por eso una consulta que busca una sola fila hace result.rows[0].
RETURNING *
Le pide a Postgres que devuelva la fila afectada por un INSERT/UPDATE, evitando un SELECT aparte después.

Decisión de diseño

JavaScript plano, no TypeScript — por ahora

Elegida

JavaScript plano — sin paso de compilación ni configuración extra mientras se aprenden las bases de Node.

Para después

TypeScript — tipos que avisan errores antes de correr, a cambio de tsconfig y un paso de compilación.

Migración futura: no es una reescritura. Se instala typescript + paquetes @types/..., se renombran los archivos a .ts, y se van agregando tipos de a poco — un archivo .ts sin anotaciones sigue compilando igual. La única fricción real: algunas librerías viejas no traen tipos propios y hay que buscarles el paquete @types correspondiente.

Decisión de diseño

npm para instalar, pnpm para el proyecto

npm viene incluido con Node, sin pasos extra — se usó para instalar pnpm de forma global (npm install -g pnpm). De acá en adelante, el proyecto en sí se maneja con pnpm: más rápido y no duplica paquetes entre proyectos distintos en el disco.

Decisión de diseño

Express, no Fastify

Los dos resuelven lo mismo (manejar las rutas HTTP del servidor). Express es el más viejo y el más usado — la mayoría de tutoriales y respuestas de la comunidad son sobre Express, lo cual importa más que la velocidad mientras se está aprendiendo de cero.

Cómo se hace

Instalar Node.js, npm y pnpm en Windows

winget install --id OpenJS.NodeJS.LTS -e

Descarga el instalador oficial de nodejs.org y lo corre. Instala Node y, de yapa, npm — vienen siempre juntos en el mismo paquete. También agrega los ejecutables al PATH de Windows.

node --version npm --version

Confirman la instalación. Dato de color: una terminal que ya estaba abierta antes de instalar no se entera del cambio de PATH sola — hay que abrir una nueva (o refrescar la variable a mano, que es lo que hubo que hacer en esta sesión).

npm install -g pnpm

Le pide a npm que traiga el paquete pnpm del repositorio público y lo instale global — disponible como comando en cualquier carpeta, no solo dentro de un proyecto.

Nota de seguridad: pnpm trae un script propio que corre automáticamente al instalarse. npm tiene una protección que bloquea por defecto que un paquete corra scripts arbitrarios durante la instalación — defensa contra paquetes maliciosos que aprovechen ese momento. Se autorizó puntualmente con npm install -g --allow-scripts=pnpm pnpm, porque pnpm es confiable.

Resultado: Node v24.19.0 (LTS), npm 11.17.0, pnpm 12.10.1.

Cómo se hace

Carpeta del proyecto y primera dependencia

mkdir backend cd backend

Carpeta separada del resto del proyecto — al lado, más adelante, va a vivir frontend.

pnpm init

Crea package.json, el documento de identidad del proyecto: nombre, versión, y la lista de dependencias que se va llenando sola. A diferencia de npm init, no hace preguntas — escribe valores por defecto directo.

pnpm add express

Descarga Express y lo agrega a package.json. De paso crea node_modules (el código real de la librería, nunca se edita a mano ni se sube a git) y pnpm-lock.yaml (fija la versión exacta instalada de cada paquete).

Concepto

¿Por qué no usamos Vite acá?

Vite es una herramienta de frontend: sirve y empaqueta código que corre en el navegador (compila JSX, da recarga rápida, arma el paquete final). Un backend con Express es JavaScript corriendo directo en Node, sin pasar por un navegador — no hay nada que empaquetar, se escribe un archivo y se corre con node archivo.js tal cual. Vite ya está anotado en el CONTEXTO.md para más adelante, cuando llegue la parte de React.

Cómo se hace

Primer servidor: index.js

js
import express from 'express';

const app = express();
const PORT = process.env.PORT || 3000;

app.get('/', (req, res) => {
  res.send('Kainos backend funcionando');
});

app.listen(PORT, () => {
  console.log(`Servidor escuchando en http://localhost:${PORT}`);
});

Scripts en package.json: "start": "node index.js" y "dev": "node --watch index.js". Corrido con pnpm dev, responde en http://localhost:3000.

Concepto

req y res son solo nombres — lo que importa es la posición

Express llama a la función de la ruta pasándole dos objetos en orden fijo: primero el pedido entrante, segundo el objeto para construir la respuesta. req/res son la convención que usa todo el mundo, pero no son especiales — (solicitud, respuesta) => respuesta.send(...) funciona idéntico. Lo que rompe todo es invertir el orden de los parámetros, no el nombre.

Decisión de diseño

node --watch en vez de nodemon

Elegida

node --watch — reinicia el proceso al guardar un archivo. Viene incluido en Node (estable desde la v20), cero dependencias nuevas.

Descartada

nodemon — paquete de terceros, más configurable (ignorar carpetas, reinicio manual), pero innecesario para un server chico.

Por qué: mismo criterio que dependencies vs devDependencies — cuanto menos haya que instalar y mantener sin una razón concreta, mejor.

Concepto

process.env.PORT || 3000: primera variable de entorno

process.env es un objeto global de Node con las variables de entorno — valores definidos por fuera del código, en el sistema operativo o por quien aloja la app. process.env.PORT vale undefined si nadie definió esa variable (como en tu máquina, ahora). El || 3000 es el operador "o": si lo de la izquierda es falsy (undefined, acá), usa 3000 como respaldo.

Por qué importa: la mayoría de los servicios de hosting (Render, Railway, Heroku) le asignan a tu app un puerto distinto cada vez mediante esa misma variable, y tu código tiene que escuchar ahí, no en uno fijo. Este patrón hace que el mismo código funcione sin cambios en tu máquina (usa 3000) y en producción (usa lo que el hosting le pase).

Cómo se hace

Conectar Node a PostgreSQL: pg, .env y Pool

pnpm add pg

Driver oficial de PostgreSQL para Node — manda SQL y devuelve filas como objetos de JS. El mismo trabajo que hace psql por consola, pero para que lo use el código.

.env
PGHOST=localhost
PGPORT=5432
PGDATABASE=kainos_dev
PGUSER=postgres
PGPASSWORD=<contraseña real>
.gitignore
node_modules
.env

El .gitignore se escribió antes de tener git siquiera inicializado — así el primer commit, el día que se haga, nunca corre riesgo de subir una contraseña.

db.js
import { Pool } from 'pg';

export const pool = new Pool({
  host: process.env.PGHOST,
  port: process.env.PGPORT,
  database: process.env.PGDATABASE,
  user: process.env.PGUSER,
  password: process.env.PGPASSWORD,
});

Pool en vez de una sola conexión: mantiene varias conexiones abiertas a Postgres y las reparte entre pedidos — un servidor real atiende varios pedidos a la vez, y no conviene que se hagan cola esperando una única conexión.

El script "dev" pasó a "node --watch --env-file=.env index.js" — la bandera --env-file es, otra vez, una función nativa de Node (no el paquete dotenv que se ve en la mayoría de los tutoriales): mismo criterio que con --watch, evitar una dependencia que Node ya resuelve solo.

Concepto

async/await: esperar sin bloquear

js
app.get('/test-db', async (req, res) => {
  const result = await pool.query('SELECT NOW()');
  res.json(result.rows[0]);
});

Una consulta a la base tarda (va por red hasta Postgres y vuelve) — pool.query(...) no devuelve el resultado al instante, devuelve una promesa de que el resultado va a llegar. await dice "pausá esta función hasta que esa promesa se resuelva, y seguí con el valor real" — por eso la función de la ruta se marca async: toda función que usa await adentro tiene que estar marcada así.

Concepto

res.json vs res.send, y por qué result.rows[0]

res.json(objeto) convierte el objeto a texto JSON y le pone a la respuesta el header Content-Type: application/json — así quien la reciba (el navegador, después el frontend React) sabe que tiene que interpretarla como datos, no como HTML. res.send manda lo que le pases tal cual y Express adivina el tipo.

result.rows es siempre un arreglo, nunca una fila pelada — porque pg no sabe de antemano si la consulta va a devolver 0, 1 o 1000 filas, así que uniformiza todo como lista. SELECT NOW() devuelve una sola fila, entonces result.rows queda como [ { now: ... } ] — un arreglo con un único objeto adentro. result.rows[0] agarra ese primer elemento, en vez de devolver el arreglo completo con los corchetes.

Concepto

Estructura en capas: cuatro responsabilidades separadas

estructura
src/
  routes/       → qué URL existe, qué método la atiende
  controllers/  → traduce HTTP ↔ negocio, nunca sabe de SQL
  services/     → reglas de negocio, nunca sabe de HTTP
  data/         → la única capa que toca pool.query(), nunca sabe de HTTP

La idea de separar: si mañana cambia Express por otra cosa, o Postgres por otro motor, se reescribe una sola capa. Y para debuggear, el tipo de problema te dice directo en qué capa mirar — un dato mal validado es services, una consulta que explota es data, un código HTTP mal puesto es controllers.

Cómo se hace

Primera rebanada, con las cuatro capas: producto

src/data/productos.data.js
import { pool } from '../../db.js';

export async function obtenerTodos() {
  const result = await pool.query(`
    SELECT p.id, p.nombre, p.tipo, p.activo, c.nombre AS categoria
    FROM producto p
    JOIN categoria c ON p.categoria_id = c.id
    WHERE p.activo = true
    ORDER BY p.id
  `);
  return result.rows;
}

export async function crear({ categoria_id, nombre, tipo }) {
  const result = await pool.query(
    'INSERT INTO producto (categoria_id, nombre, tipo) VALUES ($1, $2, $3) RETURNING *',
    [categoria_id, nombre, tipo]
  );
  return result.rows[0];
}
src/services/productos.service.js
import * as productosData from '../data/productos.data.js';
import { AppError } from '../utils/AppError.js';

export async function listar() {
  return productosData.obtenerTodos();
}

export async function crear(datos) {
  if (!datos.nombre || !datos.categoria_id || !datos.tipo) {
    throw new AppError('Faltan campos obligatorios', 400);
  }
  return productosData.crear(datos);
}
src/controllers/productos.controller.js
import * as productosService from '../services/productos.service.js';

export async function listar(req, res, next) {
  try {
    const productos = await productosService.listar();
    res.json(productos);
  } catch (err) {
    next(err);
  }
}

export async function crear(req, res, next) {
  try {
    const nuevoProducto = await productosService.crear(req.body);
    res.status(201).json(nuevoProducto);
  } catch (err) {
    next(err);
  }
}
src/routes/productos.routes.js
import { Router } from 'express';
import * as productosController from '../controllers/productos.controller.js';

export const productosRouter = Router();

productosRouter.get('/', productosController.listar);
productosRouter.post('/', productosController.crear);

Router() es una mini-app de Express que agrupa rutas relacionadas; se monta en index.js bajo un prefijo (app.use('/productos', productosRouter)). Probado: GET /productos devuelve los 4 activos con su categoría; POST /productos creó el id 5 y respondió 201.

Concepto

Consultas parametrizadas: por qué nunca armar el SQL a mano

$1, $2, $3 en el INSERT de productos.data.js son consultas parametrizadas. Nunca hay que meter un valor que viene de afuera (del req.body) directo dentro del texto de la consulta armando un string a mano — si alguien manda como "nombre" algo tipo '); DROP TABLE producto; --, con concatenación de texto ese string pasaría a ser parte del SQL ejecutado: inyección SQL. Con los parámetros aparte, pg le entrega el valor a Postgres como dato puro, nunca como código, sea lo que sea que contenga.

Concepto

Manejo de errores centralizado

src/utils/AppError.js
export class AppError extends Error {
  constructor(message, statusCode) {
    super(message);
    this.statusCode = statusCode;
  }
}
src/middleware/errorHandler.js
export function errorHandler(err, req, res, next) {
  const statusCode = err.statusCode || 500;
  console.error(err);
  res.status(statusCode).json({ error: err.message });
}

Express reconoce un middleware con exactamente 4 parámetros (err, req, res, next) como manejador de errores — solo corre cuando algo le pasa un error con next(err). Se registra una sola vez, al final de index.js, y centraliza en un solo lugar cómo se convierte cualquier error en respuesta HTTP. El patrón en cada controller es siempre try { ... } catch (err) { next(err) } — nunca se deja un error sin controlar.

app.use(express.json()) también se agregó en index.js, antes de las rutas — sin esto, req.body queda undefined en un POST, porque Express no interpreta el JSON entrante solo.

Concepto

Routers anidados y mergeParams

Para GET/POST /productos/:id/precios se armó un router propio para precio (precios.routes.js), separado de productos.routes.js — mismo criterio de "una capa, un archivo por recurso" que ya se venía siguiendo en data/service/controller.

src/routes/precios.routes.js
export const preciosRouter = Router({ mergeParams: true });

preciosRouter.get('/', preciosController.listarPrecios);
preciosRouter.post('/', preciosController.agregarPrecio);
src/routes/productos.routes.js
productosRouter.use('/:id/precios', preciosRouter);

Se discutió la alternativa de escribir el path completo (preciosRouter.get('/productos/:id/precios', ...)) montado suelto en index.js — también funciona, sin necesitar mergeParams. La diferencia real: con el path completo escrito a mano, el string '/productos' queda duplicado en dos archivos (el mount de index.js y el de precios.routes.js); si cambia el prefijo, hay que acordarse de actualizar los dos lugares. Montando preciosRouter como sub-router de productosRouter, el prefijo /productos vive en un solo lugar. mergeParams: true es lo que permite que, aun viviendo en otro archivo, preciosRouter siga viendo el :id definido por su router padre — sin esa opción, req.params.id quedaría undefined adentro de precios.controller.js.

Cómo se hace

Agregar un precio: transacción real

Cambiar un precio no es un solo paso: hay que cerrar la fila vigente (vigente_hasta) e insertar una nueva — las dos, o ninguna. Si el cierre funciona pero el alta falla, el producto queda sin ningún precio vigente.

src/data/precios.data.js
export async function cerrarVigente(client, productoId, canalId) {
  await client.query(
    `UPDATE precio
     SET vigente_hasta = GREATEST(vigente_desde, CURRENT_DATE - 1)
     WHERE producto_id = $1 AND canal_id = $2 AND vigente_hasta IS NULL`,
    [productoId, canalId]
  );
}

export async function crear(client, { producto_id, canal_id, monto }) {
  const result = await client.query(
    'INSERT INTO precio (producto_id, canal_id, monto) VALUES ($1, $2, $3) RETURNING *',
    [producto_id, canal_id, monto]
  );
  return result.rows[0];
}
src/services/precios.service.js
const client = await pool.connect();
try {
  await client.query('BEGIN');
  await precioData.cerrarVigente(client, productoId, datos.canal_id);
  const nuevoPrecio = await precioData.crear(client, {
    producto_id: productoId,
    canal_id: datos.canal_id,
    monto: datos.monto,
  });
  await client.query('COMMIT');
  return nuevoPrecio;
} catch (err) {
  await client.query('ROLLBACK');
  throw err;
} finally {
  client.release();
}

pool.connect() reserva una conexión fija y exclusiva (client), a diferencia de pool.query() que presta cualquier conexión libre y la devuelve al toque — con pool.query() dos veces seguidas, el UPDATE y el INSERT podrían terminar en dos sesiones de Postgres sin relación, y un BEGIN en una no protegería nada en la otra. Con client, BEGIN → UPDATE → INSERT → COMMIT corren todos en la misma sesión, como una unidad atómica real. Si algo falla en el medio, ROLLBACK deshace lo que se haya alcanzado a hacer. client.release() en el finally es obligatorio pase lo que pase — olvidarlo deja esa conexión "prestada" para siempre y el pool se va quedando sin conexiones disponibles.

Bug encontrado y arreglado

Vigencia invertida al cerrar un precio creado el mismo día

Primera versión de cerrarVigente restaba un día a ciegas (vigente_hasta = CURRENT_DATE - 1). Funciona si el precio venía de antes, pero si la fila se había creado hoy mismo (caso real: carga del menú y cambio de precio el mismo día), quedaba vigente_desde posterior a vigente_hasta — una vigencia que empieza después de haber terminado.

Arreglo: GREATEST(vigente_desde, CURRENT_DATE - 1) — nunca cierra con una fecha anterior a cuando esa fila empezó. Límite que queda, documentado a propósito: si un mismo precio cambia dos veces el mismo día, la fila vieja y la nueva comparten fecha y technically se "solapan" ese día en la consulta de precio vigente. No se complica el modelo (agregar hora a la vigencia) por un caso que en el negocio real no debería pasar nunca.
