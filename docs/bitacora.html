Cómo se hace

Instalar PostgreSQL y dejarlo corriendo

Instalamos PostgreSQL 18 en Windows. El instalador trae en un solo paquete el servidor, la terminal psql y pgAdmin 4 — no hace falta sumar otro cliente aparte. Al terminar queda registrado un servicio de Windows (postgresql-x64-18) que arranca solo con el sistema: no hay un botón de "prender la base" para buscar cada vez.

Binarios y psql
C:\Program Files\PostgreSQL\18\bin
Datos reales
C:\Program Files\PostgreSQL\18\data — nunca se edita a mano, todo pasa por comandos
Servicio
postgresql-x64-18, arranca con Windows

Nota: el primer intento fue con winget, que instala en silencio y no deja la contraseña del superusuario en ningún lado legible. Resetearla sin reinstalar hubiese requerido bajar temporalmente el método de autenticación del servidor — un cambio de seguridad que preferimos no automatizar. Se resolvió desinstalando y reinstalando de forma manual, eligiendo la contraseña en el propio instalador.

Concepto

Servidor, cliente, y por qué el usuario es postgres

Un servidor es un proceso que queda escuchando pedidos por red y respondiéndolos; Postgres corre así, escuchando en el puerto 5432 sobre los archivos de data. psql y pgAdmin son clientes: abren una conexión y mandan SQL como texto, nunca tocan esos archivos directamente.

postgres es el superusuario que crea el instalador — el equivalente a root a nivel base de datos. Sirve para este momento de aprender solo; una app real se conectaría con un usuario propio y permisos acotados, tarea que queda para la etapa de roles.

Cómo se hace

Crear la base del proyecto

psql
CREATE DATABASE kainos_dev;
\c kainos_dev

Meta-comandos de psql para moverse (no son SQL, el Query Tool de pgAdmin no los reconoce): \l lista bases, \dt lista tablas, \d tabla describe una tabla, \q sale.

Cómo se hace

Primera tabla: categoria

sql
CREATE TABLE categoria (
    id     INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    nombre VARCHAR(50) NOT NULL
);

La más simple del modelo: un id autonumérico y un nombre. Sin dependencias, así que puede crearse antes que cualquier otra.

Concepto

Anatomía de un CREATE TABLE: producto

sql
CREATE TABLE producto (
    id           INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    categoria_id INTEGER NOT NULL REFERENCES categoria(id),
    nombre       VARCHAR(100) NOT NULL,
    tipo         VARCHAR(10) NOT NULL CHECK (tipo IN ('simple', 'promo')),
    activo       BOOLEAN NOT NULL DEFAULT true
);
  • id — GENERATED ALWAYS AS IDENTITY reemplaza al viejo SERIAL: mismo autoincremento, pero impide pisar el valor a mano. PRIMARY KEY suma de una NOT NULL + UNIQUE + un índice.
  • categoria_id — REFERENCES es la clave foránea: Postgres valida en cada INSERT que el valor exista del otro lado, y bloquea borrar una categoría todavía referenciada.
  • nombre — VARCHAR(100): en Postgres se guarda igual que TEXT, el largo es solo un tope de seguridad, no cambia el rendimiento.
  • tipo — CHECK (tipo IN (...)) funciona como un enum casero: solo permite esos dos valores exactos.
  • activo — DEFAULT true completa el valor solo si el INSERT lo omite; es independiente de NOT NULL, que solo prohíbe un NULL explícito.

Decisión de diseño

¿Dónde va el sabor del helado?

El pote entero de un sabor ya es un INSUMO aparte, medido en potes cerrados. Faltaba resolver si el sabor que pide el cliente aparece también como PRODUCTO distinto.

Elegida

Opción A — producto distingue solo por tamaño ("Helado 1/4 kg"). El sabor no queda estructurado en el pedido.

Descartada

Opción B — una fila de producto por tamaño × sabor. Explota precio (tamaño × sabor × canal × vigencia).

Por qué: el stock de potes no se descuenta por venta sino por apertura manual, así que "sabor más vendido" vía pedidos tampoco sería confiable del todo. Si hace falta esa analítica más adelante, se puede sumar pedido_item_sabor sin tocar catálogo ni precios.

Cómo se hace

Cargar datos y mirarlos

sql
INSERT INTO categoria (nombre) VALUES
    ('Helados'), ('Cafeteria'), ('Bebidas'), ('Comidas');

INSERT INTO producto (categoria_id, nombre, tipo) VALUES
    (1, 'Helado 1/4 kg', 'simple'),
    (1, 'Helado 1/2 kg', 'simple');

SELECT * FROM categoria;

El id nunca se menciona en el INSERT — lo genera la IDENTITY sola. activo tampoco hace falta nombrarlo: queda en true por el DEFAULT.

Concepto

El primer JOIN

sql
SELECT p.nombre, p.tipo, c.nombre AS categoria
FROM producto p
JOIN categoria c ON p.categoria_id = c.id;

JOIN sin apellido es INNER JOIN: por cada fila de producto busca en categoria la fila cuyo id coincide con categoria_id, y las pega en una sola. p y c son alias de tabla — FROM producto p ya es la forma corta de FROM producto AS p, el AS es opcional.

Existe la forma vieja con coma (FROM producto p, categoria c WHERE p.categoria_id = c.id), pero mezcla la condición de relación con los filtros de negocio en el mismo WHERE — fácil de olvidar y terminar con un producto cartesiano. JOIN ... ON separa las dos cosas a propósito.

Cómo se hace

El patrón de vigencia en código: canal y precio

sql
CREATE TABLE canal (
    id     INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    nombre VARCHAR(20) NOT NULL
);

CREATE TABLE precio (
    id             INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    producto_id    INTEGER NOT NULL REFERENCES producto(id),
    canal_id       INTEGER NOT NULL REFERENCES canal(id),
    monto          NUMERIC(10,2) NOT NULL CHECK (monto > 0),
    vigente_desde  DATE NOT NULL DEFAULT CURRENT_DATE,
    vigente_hasta  DATE
);
  • monto es NUMERIC(10,2), nunca FLOAT: la plata necesita precisión decimal exacta, un flotante binario redondea con error de centavos.
  • vigente_hasta es la única columna sin NOT NULL a propósito — NULL ahí significa "vigente hoy", no "dato faltante".
  • Dos FK en la misma tabla (producto_id, canal_id) no tienen problema en convivir, cada una se valida por separado.

Concepto

Primera consulta crítica: precio vigente hoy

sql
SELECT monto
FROM precio
WHERE producto_id = 3
  AND canal_id = 3
  AND vigente_desde <= CURRENT_DATE
  AND (vigente_hasta IS NULL OR vigente_hasta >= CURRENT_DATE);

El OR vigente_hasta IS NULL es imprescindible: en SQL, comparar cualquier cosa contra NULL (por ejemplo vigente_hasta >= CURRENT_DATE cuando es NULL) da NULL, ni verdadero ni falso — sin ese OR, las filas todavía vigentes quedarían afuera del resultado.

Concepto

Relaciones muchos a muchos: adicional

sql
CREATE TABLE adicional (
    id     INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    nombre VARCHAR(50) NOT NULL,
    activo BOOLEAN NOT NULL DEFAULT true
);

CREATE TABLE producto_adicional (
    producto_id  INTEGER NOT NULL REFERENCES producto(id),
    adicional_id INTEGER NOT NULL REFERENCES adicional(id),
    PRIMARY KEY (producto_id, adicional_id)
);

CREATE TABLE adicional_precio (
    id            INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    adicional_id  INTEGER NOT NULL REFERENCES adicional(id),
    canal_id      INTEGER NOT NULL REFERENCES canal(id),
    monto         NUMERIC(10,2) NOT NULL CHECK (monto > 0),
    vigente_desde DATE NOT NULL DEFAULT CURRENT_DATE,
    vigente_hasta DATE
);

Un producto puede admitir varios adicionales, y un mismo adicional puede servir para varios productos — eso no se resuelve con una FK de un lado solo. producto_adicional es una tabla intermedia: no representa una cosa del negocio, solo la relación. Como cada combinación tiene que ser única, no lleva id propio — la PRIMARY KEY (producto_id, adicional_id) compuesta es la que impide duplicados. adicional_precio reutiliza el mismo patrón de vigencia que precio, ahora colgando de adicional.

Concepto

Una tabla que se referencia a sí misma: promo_componente

sql
CREATE TABLE promo_componente (
    promo_id      INTEGER NOT NULL REFERENCES producto(id),
    componente_id INTEGER NOT NULL REFERENCES producto(id),
    cantidad      INTEGER NOT NULL CHECK (cantidad > 0),
    PRIMARY KEY (promo_id, componente_id)
);

Una promo es una fila de producto más (con tipo = 'promo'), distinta de las filas que la componen. Ejemplo con un combo de café + jugo + tostada: la promo entra como un producto nuevo (id propio, ej. 10), promo_componente guarda tres filas (10, café), (10, jugo), (10, tostada), y la promo tiene su propio precio en precio — no la suma de las partes. Al venderla, PEDIDO_ITEM lleva una sola línea (la promo); para descontar stock se recorre promo_componente y de ahí la RECETA de cada parte.

Punto flojo: ninguna CHECK impide cargar un promo_id que en realidad sea tipo = 'simple', o un componente que sea otra promo — Postgres no permite subconsultas dentro de un CHECK. Queda como disciplina de carga por ahora; se podría reforzar más adelante con un trigger.

Cómo se hace

Arranca el bloque de stock: insumo

sql
CREATE TABLE insumo (
    id           INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    nombre       VARCHAR(100) NOT NULL,
    tipo         VARCHAR(15) NOT NULL CHECK (tipo IN ('pote', 'bebida', 'comida', 'descartable')),
    unidad       VARCHAR(20) NOT NULL,
    stock_actual NUMERIC(10,2) NOT NULL DEFAULT 0,
    activo       BOOLEAN NOT NULL DEFAULT true
);

unidad es texto libre ("pote", "unidad", "kg") — a diferencia de tipo, la lista de unidades posibles es abierta, no una regla de negocio para validar con CHECK.

Concepto

stock_actual es un valor cacheado, no la verdad

La fuente real de verdad del stock va a ser MOVIMIENTO_STOCK (filas inmutables, cantidad con signo) — el stock real de un insumo es, en rigor, la suma de sus movimientos. stock_actual es una copia de ese resultado, guardada aparte para no tener que sumar todo el historial cada vez que alguien quiere ver cuánto queda de algo.

Riesgo: si un movimiento se inserta sin actualizar stock_actual en la misma transacción, los dos números se desincronizan. Se resuelve cuando ambas escrituras viven juntas, nunca por separado.

Decisión de diseño

Conteo físico semanal, sin tabla nueva

La idea de llevar un "stock real" contado a mano cada semana, además del calculado, no necesita una columna aparte — se resuelve con un movimiento más del libro mayor.

Cómo: cuando lo contado y stock_actual no coinciden, se inserta un MOVIMIENTO_STOCK de tipo = 'ajuste' con la diferencia. Actualiza el cacheado como cualquier otro movimiento, y además deja registrado cuándo y cuánto se desvió — más útil que solo corregir el número, porque permite notar patrones (ajustes negativos repetidos = mermas que no se están cargando).

Concepto

RECETA: la ausencia también es información

sql
CREATE TABLE receta (
    producto_id INTEGER NOT NULL REFERENCES producto(id),
    insumo_id   INTEGER NOT NULL REFERENCES insumo(id),
    cantidad    NUMERIC(10,2) NOT NULL CHECK (cantidad > 0),
    PRIMARY KEY (producto_id, insumo_id)
);

Mismo patrón de clave compuesta que producto_adicional y promo_componente. Lo importante no es la estructura sino la regla: sin fila en receta, la venta de ese producto nunca descuenta stock solo. Es la forma en que la decisión del sabor de helado (sesión 1) se vuelve real en el esquema — "Helado 1/4 kg" simplemente no tiene receta; su stock se mueve aparte, por apertura de pote.

Decisión de diseño

¿Cuándo se descuenta el stock de una venta?

Elegida

Al cerrar el pedido — agregar o sacar un item de una mesa abierta es un simple INSERT/DELETE, sin generar ni revertir movimientos.

Descartada

Al agregar cada item — refleja el stock en tiempo real, pero exige un movimiento inverso cada vez que se anula un item.

Costo asumido: mientras dos mesas tienen pedidos abiertos, ninguna sabe que la otra está comprometiendo el mismo insumo — si el último poco de un sabor se vende por partida doble, no se detecta hasta el cierre. Para 13 mesas de un local familiar es un riesgo chico y aceptado a conciencia; no lo sería para una cadena de alto volumen.

Concepto

Un problema de orden: MOVIMIENTO_STOCK tiene que esperar

MOVIMIENTO_STOCK lleva FK hacia COMPRA_ITEM y PEDIDO_ITEM — y PEDIDO_ITEM ni siquiera es del bloque de stock, es del bloque de mesas y pedidos, el último del modelo. No es un error: es una propiedad real del esquema, MOVIMIENTO_STOCK es la tabla bisagra entre los tres bloques, así que se construye al final, después de terminar compras y pedidos. El orden de trabajo quedó así: compras → pedidos → recién entonces movimiento_stock.

Cómo se hace

Proveedores y compras: cabecera + detalle

sql
CREATE TABLE proveedor (
    id       INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    nombre   VARCHAR(100) NOT NULL,
    contacto VARCHAR(100)
);

CREATE TABLE insumo_proveedor (
    insumo_id    INTEGER NOT NULL REFERENCES insumo(id),
    proveedor_id INTEGER NOT NULL REFERENCES proveedor(id),
    codigo       VARCHAR(50),
    costo        NUMERIC(10,2) NOT NULL CHECK (costo > 0),
    PRIMARY KEY (insumo_id, proveedor_id)
);

CREATE TABLE compra (
    id           INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    proveedor_id INTEGER NOT NULL REFERENCES proveedor(id),
    fecha        DATE NOT NULL DEFAULT CURRENT_DATE
);

CREATE TABLE compra_item (
    id         INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    compra_id  INTEGER NOT NULL REFERENCES compra(id),
    insumo_id  INTEGER NOT NULL REFERENCES insumo(id),
    cantidad   NUMERIC(10,2) NOT NULL CHECK (cantidad > 0),
    costo_unit NUMERIC(10,2) NOT NULL CHECK (costo_unit > 0)
);
  • proveedor.contacto — primera columna de texto libre sin NOT NULL a propósito: dato real que puede no estar disponible al cargar el proveedor.
  • insumo_proveedor — misma clave compuesta de siempre, pero esta vez la tabla de relación también carga datos propios (codigo, costo), no solo la relación pelada.
  • compra / compra_item — patrón cabecera/detalle: una compra trae varios insumos juntos, por eso son dos tablas (va a repetirse igual en pedido/pedido_item).
  • costo_unit se congela en la línea de compra — igual que precio_unit en las ventas, para que un aumento de proveedor no altere compras ya hechas ni rompa el cálculo de márgenes históricos.

Cómo se hace

Bloque de mesas y pedidos: mesa, pedido, pedido_item, pedido_item_adicional

sql
CREATE TABLE mesa (
    id     INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    numero INTEGER NOT NULL UNIQUE,
    activa BOOLEAN NOT NULL DEFAULT true
);

CREATE TABLE pedido (
    id         INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    canal_id   INTEGER NOT NULL REFERENCES canal(id),
    mesa_id    INTEGER REFERENCES mesa(id),
    estado     VARCHAR(10) NOT NULL DEFAULT 'abierto' CHECK (estado IN ('abierto', 'cerrado', 'anulado')),
    id_externo VARCHAR(50),
    comision   NUMERIC(10,2) CHECK (comision >= 0),
    creado_en  TIMESTAMP NOT NULL DEFAULT now(),
    cerrado_en TIMESTAMP
);

CREATE TABLE pedido_item (
    id          INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    pedido_id   INTEGER NOT NULL REFERENCES pedido(id),
    producto_id INTEGER NOT NULL REFERENCES producto(id),
    cantidad    INTEGER NOT NULL CHECK (cantidad > 0),
    precio_unit NUMERIC(10,2) NOT NULL CHECK (precio_unit > 0)
);

CREATE TABLE pedido_item_adicional (
    pedido_item_id INTEGER NOT NULL REFERENCES pedido_item(id),
    adicional_id   INTEGER NOT NULL REFERENCES adicional(id),
    precio_unit    NUMERIC(10,2) NOT NULL CHECK (precio_unit > 0),
    PRIMARY KEY (pedido_item_id, adicional_id)
);
  • mesa_id, id_externo, comision sin NOT NULL a propósito — nulos en mostrador/apps según corresponda (decisión 10 del contexto).
  • TIMESTAMP (fecha + hora) aparece por primera vez, en creado_en/cerrado_en — hasta ahora solo habíamos usado DATE (sin hora) para vigencias.
  • estado DEFAULT 'abierto' CHECK (...) combina lo ya conocido (enum casero) con un valor inicial, para que un pedido nazca abierto sin que el código tenga que decirlo.
